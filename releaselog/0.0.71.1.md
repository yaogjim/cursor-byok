# Gateway-byok v0.0.71.1

本版本完成「0.0.71.0 对话连接回归修复」：修复 0.0.71.0 双渠道移植引入的 BidiAppend/RunSSE 分流解析缺陷——未处理 HTTP `Content-Encoding: gzip` 与 `application/json` 编码导致真实 Cursor 请求全部 502、RunSSE 等待 60 秒后取消。交付状态 `verified-partial`：两个相关包完整测试、定向 race、vet 与 Host 级 gzip→模拟 provider 回复契约验证通过；真实 Cursor 官方/Auto/BYOK 实机首段回复验收待完成。

## 回归取证（详见 docs/process.md）

- 下载样本 841 条事件：56 次后端 `bidi_append` 全部 502（handler_error），7 次已结束 `run_sse` 均约 60 秒后 canceled，无任何 upstream/provider 调用事件；本机 0.0.71.0 会话同型 8 次 502，而回退 0.0.61.1 的快照已有 226 次 BidiAppend 200。
- 根因（隔离复现证实）：`agent_route.go` 的 BidiAppend/RunSSE 解析调用 `extractCatalogProtoPayload(contentType, "", body)` 未传 HTTP Content-Encoding，并固定 `proto.Unmarshal` 不区分 JSON。旧入口 `connect.NewUnaryHandler` 能正确读取这些合法 unary 编码，而 0.0.71.0 新增的前置分流在它之前失败；路由尚未 Remember，先到的 RunSSE 因而持续等待。四种身份/选模×三种编码共 12 例，原源码 8 失败、4 通过。

## 修复内容

- `agent_action.go`：`routeBidiAppend`/`routeRunSSE` 传入真实 HTTP `Content-Encoding`（新增 `inboundContentEncoding` 从 Headers 或原始 Request 读取）。
- `agent_route.go`：新增 `decodeAgentRoutePayload` 在只读副本上依次处理 HTTP gzip 解压、Connect 帧（帧压缩与 HTTP 整体压缩区分）、再按实际媒体类型解码；`unmarshalAgentRouteMessage` 按 Content-Type 区分 protobuf 与 JSON（`protojson` + `DiscardUnknown`）。不支持/损坏编码明确报错，不猜渠道。
- 原始请求体、Content-Type、Content-Encoding 与身份仍原样用于后续转发；选模、会话归属、超时、账号和证书逻辑不变。转发链路零改动。

## 回归测试（先红后绿）

- `agent_route_test.go` 固化四种身份/选模（纯本地选 BYOK、官方身份选 BYOK、官方身份选官方、官方身份选 Auto）×三种编码（未压缩 Protobuf、HTTP gzip Protobuf、JSON）共 12 组合，以及真实 Connect 解码、流先到、原始请求保留、损坏/不支持编码和帧压缩。
- `cursor_contract_test.go` 新增 `TestGatewayDuoHostGzipUnaryWire`：普通 BYOK 收到模拟模型回复、gzip 请求此前返回 502，修复后通过。
